## Outcome: structurally complete, blocked by ADR-012 (REG_ALLOC)

The function is fully reconstructed. The residual is **pure context-dependent
register-allocation drift** (verified at instruction level): the inlined `gcDesiredValue`
release path lands the tagged handle in `$t1` where the original monolithic gcAll_psp.obj
TU used `$t0`, plus a matching `ori` tail-duplication, repeated across ~20 dances. That
de-aligns the body, inflating the raw diff to 4186/5640 despite identical structure. This
is exactly `docs/decisions/012-snc-context-dependent-regalloc.md` /
`docs/research/snc-register-allocation.md`: SNC's allocator carries state across functions
within a TU; our split TU gives different tie-breaks. No local source leverage exists.

Marked `failed` (category=REG_ALLOC). Source committed as the split-TU file
`src/gcDoEntitySpawn_operator_eq.cpp` (ODR-WARNING; does not touch the canonical file or
headers — the 6 existing matches in `src/gcDoEntitySpawn.cpp` reverify clean).

### New finding — the size lever

Declaring `unsigned int handle = t0;` as the first statement inside the `gcDesiredValue`
release guard (base still computed from `t0`, but the post-store null-test and vtable
deref reading `handle`) forces SNC to emit the original's handle-preserve move pair
(`move a2,a1 ; move a1,tN`) and brings the symbol to exactly 5640B. Without it SNC keeps
one copy in a high temp and the function is 88B short.

## CG_LRA patch workflow — outcome: NO patch, and ADR-012 misdiagnosis corrected

The patch workflow (flag-lever probe ‖ CG_LRA reverse-engineering → prototype+gate) returned
a definitive, verified verdict. `extern/snc/pspcor.exe` untouched (md5
770828490878f4a30081d75a91be3722); all experiments on removed copies.

**Flag levers exhausted (no zero-blast-radius fix):** `-Xgprreserve=N` swept N=2..23 — none
fix size or reduce the diff; reserving t0/t1 is a no-op on the first-fit tie-break.
`-Xbindreg` only binds long-term callee-saves (r21/r22), cannot target an inlined temp.
`-Xfprreserve` is FP-only. A per-file CFLAGS line cannot reach the decision.

**CG_LRA map (RE, read-only, capstone PE disassembler).** pspcor.exe ImageBase 0x400000.
Per-routine CG driver 0x415939; phases: CG_expand=0x41ac63, CG_sched=0x427418,
**CG_LRA=0x496bd9** → main allocator 0x495f76 → priority-coloring driver **0x45d3e0**
("attempt priority coloring" xref 0x45d445) → physical-register first-fit at **0x454cdd**
(scan 0x454d27–0x454d52 against selection bitmap 0x4f8908), register-class descriptor table
at **0x4ddab0** (stride 0x34; single-reg/pair entries, NOT a tunable priority array).
Per-routine alloc init at 0x493c81 zeroes the alloc globals each routine.

**Root-cause hypothesis DISPROVEN (the important finding).** Earlier rounds (and ADR-012)
attributed this to TU-context-dependent allocation seeded by the monotonic routine-ID counter
at **0x5032d8**. Direct measurement refutes this *for this function*:
- Freezing the counter increment at 0x4158eb → output byte-identical to stock.
- Sweeping the stamped routine ID (0x4158e2) across {0,1,5,17,100,1000,5000,9000,32768,
  65535,131072} → every value byte-identical.
- Prepending 2 / 40 / integer-register-heavy / float-heavy functions ahead of the target in
  the same TU → byte-identical in all four cases. **Independently re-verified** here via
  `tu_context_harness.py` (prepended heavy fn vs standalone: identical 4186-word diff,
  symbol_size 5648).

So `gcDoEntitySpawn::operator=` is **context-INDEPENDENT**: the `$t1` + `ori`-tail-dup
codegen is **intrinsic to our reconstructed source**, hence **source-controllable** — not the
ADR-012 wall. (This does not necessarily overturn ADR-012's Collide evidence; it is a
per-function measurement. ADR-012 is point-in-time and left intact; this correction lives
here.) The committed source's earlier "ADR-012 wall / no source leverage" header was wrong and
has been corrected. Note the true emitted size is **5648B** (8B over), first diff at **0xF8**.

**No surgical patch exists** regardless: the only levers (first-fit order 0x454cdd, priority
metric 0x45d3e0, numbering) are global to every function and would mass-regress the 5012; a
TU-position-independent numbering normalization is a large global research project, not a
surgical fix, and is moot here since context is not the cause.

**Open problem (the real path to 100%):** find the *source structure* of `operator=` /
the inlined `gcDesiredValue::operator=` that makes SNC place the handle in `$t0` and emit the
original's base-computation branch layout (`and $t0` before the `b`, no tail-dup). Because the
function is context-independent, a single-dance min-repro is faithful and iteration is
reliable — this is ordinary (if hard) source-matching work, no compiler patch needed.
